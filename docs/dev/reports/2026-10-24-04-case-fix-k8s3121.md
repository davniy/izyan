| Effect | `Index.FindSymbol` -> `loadExtra` -> `packages.Load` failed, so both advisory symbols were reported "not found in source" |

## Fix

Bounded vendored-source fallback (`internal/goanalysis/vendorsource.go`, `internal/rootcause/rootcause.go`):

- Typed `findSymbol` runs first, unchanged.
- Only on a **loader failure** (error that is neither `ErrSymbolNotFoundInPackage` nor `ErrAmbiguousSymbol`) does it parse `<snapshot>/vendor/<import path>` with `go/parser` and resolve the same symbol forms the typed path resolves.
- A vendored hit is verified and carries the limitation `symbol <pkg>.<sym> verified against vendored source (Go loader unavailable: <err>)`.
- A miss keeps the original loader error and never invents absence. `Absent` semantics are untouched: only a cleanly decoded `go list -deps` set may resolve by absence.
- `FindSymbol` itself is unchanged, so unrelated consumers keep today's behavior.

## Assessment

The loader failure no longer masquerades as symbol absence. That was the actual defect: the analyzer had no root cause at all and could not have found anything.

The remaining `INCONCLUSIVE` is a **different, legitimate** blocker: the vulnerable symbols are code-generator internals (`plugin/unmarshal`), so no product call path exists to them; `C-REACH`/`C-LOCUS` stay `UNKNOWN` rather than `FALSE`, because the build graph could not be measured (`go list -deps` still fails) and the analyzer cannot prove unreachability without it.

This is not a new safety regression and not a false-safe. To reach a true positive on this case, the analyzer would need the `go list -deps` graph to succeed (a build-scope problem, not a symbol-lookup problem) and then either a real call path or a verified absence.
