# Спецификация: переработка triage и человекочитаемого отчёта Izyan

## 1. Контекст

Текущий `report.md` перегружен внутренними деталями анализатора и смешивает в одном документе:

- итоговый verdict;
- исходную критичность advisory;
- контекстную оценку риска;
- приоритет исправления;
- альтернативные сценарии для других окружений;
- машинные гипотезы;
- Evidence IDs и внутренние claims;
- результаты детерминированных инструментов;
- потенциальный LLM-анализ;
- технический аудит выполнения.

Из-за этого основной вывод трудно понять даже после нескольких прочтений.

На примере отчёта по `GO-2022-0603` проявляются дополнительные логические проблемы:

- исходный приоритет `P2 (Medium)` повышается до `P0 (Blocker)`;
- исходная `MEDIUM` может быть повышена до `CRITICAL`;
- в отчёте присутствует внутренний статус `ASSESSED`, непонятный конечному пользователю;
- блок называется «Обоснование переоценки», хотя переоценка может происходить в сторону повышения;
- гипотетический внутренний Mesh отображается как отдельный `NO_EXPLOIT_PATH_FOUND / DISMISSED`, хотя эта среда фактически не была подтверждена;
- одновременно присутствуют итоговый verdict `EXPLOITABLE` и машинная рекомендация «МОЖНО ОТКЛОНИТЬ ПОСЛЕ ПОДТВЕРЖДЕНИЯ»;
- методология упоминает LLM-анализ, хотя в конкретном запуске LLM может быть отключена;
- суть самой уязвимости и реальная цепочка эксплуатации раскрыты хуже, чем внутренние детали анализа;
- Evidence Register, Claims, Data Flows и другие служебные структуры занимают значительную часть отчёта и мешают восприятию.

## 2. Цель

Сделать основной отчёт Izyan понятным разработчику, AppSec-специалисту и владельцу компонента без знания внутренней архитектуры анализатора.

Первые 1–2 экрана отчёта должны отвечать на вопросы:

1. Что это за уязвимость?
2. Применима ли она к текущему продукту?
3. Эксплуатируема ли она?
4. Почему Izyan пришёл к такому выводу?
5. Меняется ли исходный приоритет?
6. Что нужно сделать?
7. Какие неизвестные факторы могут изменить вывод?

Все внутренние технические детали должны оставаться доступными для аудита, но не мешать чтению основного отчёта.

# 3. Основные инварианты

## 3.1. Контекстный анализ не усиливает исходную оценку

Izyan может:

- подтвердить исходную критичность / приоритет;
- понизить критичность / приоритет;
- снять finding при наличии достаточного доказательства;
- оставить оценку без изменения при недостатке оснований для понижения.

Izyan **не должен автоматически повышать**:

- severity;
- CVSS-like score;
- remediation priority.

Примеры:

- `MEDIUM / P2` → `MEDIUM / P2` — допустимо;
- `CRITICAL / P0` → `MEDIUM / P2` — допустимо при доказанном снижении риска;
- `MEDIUM / P2` → `CRITICAL / P0` — запрещено;
- `HIGH / P1` → `P0` — запрещено.

Если анализ выявил опасный публичный exposure, это означает:

> оснований для понижения исходной оценки не найдено.

Это не является основанием самостоятельно повышать advisory severity.

## 3.2. Severity advisory и результат Izyan — разные сущности

Исходная severity является свойством advisory / scanner input.

Izyan отвечает на другой вопрос:

> применима ли уязвимость к этому продукту и есть ли основания изменить приоритет её устранения.

В human-readable отчёте не следует создавать впечатление, что Izyan пересчитывает CVSS как полноценный CVSS-калькулятор.

## 3.3. Гипотетическая среда не является доказанным verdict

Если анализ выполнялся по исходному коду и не содержит достоверной информации о production deployment, нельзя писать:

- `Internal Mesh → NO_EXPLOIT_PATH_FOUND`;
- `Internal Cluster → DISMISSED`;
- «действий не требуется».

Вместо этого необходимо писать:

> Если в целевой среде подтверждено ограничение X, оно может быть основанием для повторной оценки / снижения приоритета.

Альтернативная среда — это условие для возможной переоценки, а не отдельный автоматически вынесенный verdict.

## 3.4. Финальный verdict имеет приоритет над машинными гипотезами

После вынесения финального verdict основной отчёт не должен содержать рядом с ним противоположные рекомендации.

Например, при:

`EXPLOITABLE`

нельзя в основном отчёте показывать:

`МОЖНО ОТКЛОНИТЬ ПОСЛЕ ПОДТВЕРЖДЕНИЯ`.

Machine proposals могут быть сохранены:

- в audit report;
- в JSON;
- в разделе для эксперта;

но должны быть явно обозначены как внутренние гипотезы, не изменяющие текущий verdict.

## 3.5. Отчёт должен показывать фактически выполненный анализ

Если LLM не использовалась, основной отчёт должен явно говорить:

`LLM-анализ в данном запуске не выполнялся.`

Нельзя выводить общий текст про «семантический анализ LLM» так, будто такой анализ был выполнен.

Если LLM использовалась, в отчёте должны быть видны:

- какие задачи ей передавались;
- какие выводы она предложила;
- какие из них были приняты;
- какие отклонены;
- какие подтверждены детерминированными проверками.

LLM-вывод сам по себе не является доказательством безопасного verdict.

# 4. Изменение модели triage

## 4.1. Отказ от усиления severity

Текущая логика `internal/risk/risk.go` должна быть изменена.

Контекстный результат должен ограничиваться исходной оценкой сверху:

```text
contextual_severity <= base_severity
contextual_priority <= base_priority
```

Здесь `<=` означает «не более критично».

## 4.2. Рекомендуемая семантика

### NOT_AFFECTED

Результат:

- finding может быть закрыт;
- remediation priority → `DISMISSED`;
- причина закрытия должна быть доказана.

Примеры:

- версия не входит в affected range;
- модуль отсутствует;
- уязвимый пакет не входит в релизную сборку.

### NO_EXPLOIT_PATH_FOUND

Результат:

- допускается закрытие finding только при выполнении существующего safety-инварианта Izyan;
- обязательное условие эксплуатации должно быть опровергнуто доказуемым falsifier + negative verification;
- отсутствие найденного пути не является достаточным основанием.

### EXPLOITABLE

Результат:

- finding остаётся открытым;
- базовая severity не повышается;
- исходный priority может быть сохранён;
- при наличии доказанных mitigating controls допускается только понижение priority.

### INCONCLUSIVE

Результат:

- исходная severity сохраняется;
- исходный remediation priority не должен автоматически снижаться;
- отчёт должен перечислить, каких данных не хватает для решения.

## 4.3. Contextual score

Числовой `ContextualScore` не должен отображаться в основном `report.md`, если он не является результатом стандартизированного расчёта.

Допускается сохранить поле в JSON для обратной совместимости, но не использовать его как псевдо-CVSS.

В дальнейшем предпочтительно заменить его на:

```text
triage_disposition:
  unchanged
  lowered
  dismissed
  inconclusive
```

и отдельно хранить:

```text
base_severity
base_priority
effective_priority
```

# 5. Новый основной report.md

Основной отчёт должен быть коротким и человекочитаемым.

Предлагаемая структура:

```text
# <VULN-ID> — <краткая суть уязвимости>

## Результат

## В чём уязвимость

## Почему она применима / не применима к этому продукту

## Что подтверждено

## Что не удалось подтвердить

## Оценка и приоритет

## Рекомендация по исправлению

## Использование AI

## Ссылка на технический аудит
```

# 6. Раздел «Результат»

Пример для подтверждённой уязвимости:

```markdown
## Результат: EXPLOITABLE

Уязвимость применима к текущей сборке и путь эксплуатации подтверждён.

**Исходная критичность:** MEDIUM, CVSS 5.0  
**Приоритет:** P2 — без изменения

Контекстный анализ не выявил оснований для снижения исходной оценки.
```

Пример для снижения:

```markdown
## Результат: EXPLOITABLE

Уязвимость технически эксплуатируема, но подтверждённый контекст
развёртывания ограничивает доступ к уязвимой поверхности.

**Исходный приоритет:** P0  
**Приоритет после triage:** P2

### Почему приоритет снижен

- endpoint доступен только через loopback;
- внешние клиенты не имеют сетевого пути к нему;
- это подтверждено конфигурацией deployment.
```

Если оценка не снижена, раздел «Почему приоритет снижен» отсутствует.

# 7. Удалить «Статус оценки» из human report

Не показывать в `report.md`:

```text
Номинальный
ASSESSED
PROVISIONAL
NOT_APPLICABLE
```

Эти значения являются внутренним состоянием модели анализа.

При необходимости они сохраняются в:

- `report.json`;
- audit report;
- API.

Для человека они должны быть выражены нормальным текстом:

- «оценка не изменена»;
- «приоритет снижен»;
- «finding можно закрыть»;
- «требуется дополнительная проверка».

# 8. Раздел «В чём уязвимость»

Отчёт должен объяснять **механизм дефекта**, а не только ссылаться на advisory.

Недостаточно:

```text
GO-2022-0603 — заявлена как уязвимая в базе.
```

Нужно формировать объяснение вида:

```text
Уязвимая версия gopkg.in/yaml.v3 может аварийно завершить процесс
при обработке специально сформированного YAML в yaml.Unmarshal.

В данном приложении тело HTTP-запроса передаётся в yaml.Unmarshal.
Поэтому клиент, имеющий доступ к endpoint, может передать такой YAML
и вызвать panic, нарушив доступность сервиса.
```

Требования:

- краткое описание дефекта;
- уязвимая операция / функция;
- путь пользовательского или внешнего ввода;
- фактическое последствие;
- связь между advisory и кодом продукта.

Если механизм не удалось установить, это должно быть явно написано.

---

# 9. Раздел «Что подтверждено»

Вместо Claims + Evidence IDs в основном отчёте выводить человеческие факты.

Пример:

```markdown
## Что подтверждено

- используется уязвимая версия `gopkg.in/yaml.v3`;
- пакет с уязвимым кодом входит в релизную сборку;
- найден путь вызова из приложения до `yaml.Unmarshal`;
- тело HTTP-запроса достигает `yaml.Unmarshal`;
- приложение создаёт listener на `:8080`;
- обязательные условия эксплуатации подтверждены.
```

Не показывать здесь:

- `C-REACH`;
- `C-LOCUS`;
- `C-CONSTRAINT`;
- `EV-008`;
- `EV-019`;
- `SinkClosure`;
- внутренние DTO / enum names.

Они остаются в audit report.

---

# 10. Раздел «Что не удалось подтвердить»

Этот блок должен отражать границы конкретного анализа.

Пример:

```markdown
## Что не удалось подтвердить

По анализируемому репозиторию не удалось определить фактический сетевой
периметр production deployment.

Внешние ограничения доступа могут находиться вне репозитория, например:

- Kubernetes NetworkPolicy;
- Istio AuthorizationPolicy;
- Ingress / API Gateway;
- firewall;
- отдельные deployment-манифесты.

Если такие ограничения подтверждены для целевой среды, они могут быть
учтены при повторном triage.
```

Ключевой принцип:

> неизвестный факт не превращается ни в доказательство эксплуатации, ни в доказательство безопасности.

# 11. Отображение разных сред

Удалить текущую модель вида:

| Среда | Verdict | Priority |
|---|---|---|
| Public | EXPLOITABLE | P0 |
| Internal Mesh | NO_EXPLOIT_PATH_FOUND | DISMISSED |

Заменить на блок:

```markdown
## Что может изменить оценку

Текущий вывод сделан для обнаруженного в исходном коде listener `:8080`.

Приоритет может быть пересмотрен, если для фактической production-среды
будет подтверждено, что недоверенный клиент не имеет сетевого пути к
этому endpoint.

Для этого можно предоставить deployment-манифесты или явно указать
целевой perimeter.
```

Допускается перечислять несколько сценариев:

```text
Среда              Что нужно подтвердить                    Возможный эффект
Public             Дополнительных ограничений нет           Оценка без изменения
Internal cluster   Запрет доступа недоверенных workloads    Возможное снижение
Loopback only      Listener действительно 127.0.0.1         Возможное снижение
```

Колонка не должна содержать финальные verdict до проверки факта.

# 12. Рекомендация по исправлению

Раздел должен быть коротким и actionable.

Пример:

```markdown
## Исправление

Рекомендуемый вариант — обновить зависимость:

`gopkg.in/yaml.v3`
`v3.0.0-20210107192922-496545a6307b`
→
`v3.0.0-20220521103104-8f96da9f5d5e`

Команды:

    go get gopkg.in/yaml.v3@v3.0.0-20220521103104-8f96da9f5d5e
    go mod tidy
```

Допустимо перечислить compensating controls, но они не должны автоматически приравниваться к исправлению уязвимого dependency.

Удалить строки вида:

```text
Текст выше можно использовать в задаче трекера...
```

Сам отчёт уже должен быть пригоден для копирования в tracker без дополнительных метакомментариев.

# 13. Использование AI / LLM

В основном отчёте должен быть отдельный короткий раздел.

## Если LLM не использовалась

```markdown
## Использование AI

LLM-анализ в данном запуске не выполнялся.
Все выводы основаны на детерминированных проверках и статическом анализе.
```

## Если LLM использовалась

```markdown
## Использование AI

LLM использовалась для:
- анализа patch semantics;
- классификации роли функций;
- формирования гипотез.

Принятые выводы:
- ...

Отклонённые / неподтверждённые:
- ...

Ни один отрицательный verdict не основан только на выводе LLM.
```

Нельзя просто перечислять capability анализатора, которая в конкретном запуске не использовалась.

# 14. Разделение human report и audit report

## report.md

Предназначен для:

- разработчика;
- AppSec;
- владельца сервиса;
- задачи в tracker.

Содержит только:

- verdict;
- суть дефекта;
- применимость;
- ключевые подтверждённые факты;
- неопределённости;
- triage;
- remediation;
- AI usage.

## report.audit.md

Предназначен для:

- отладки Izyan;
- эксперта;
- воспроизводимости;
- аудита решения.

Перенести туда:

- полный Claims table;
- Evidence Register;
- Evidence IDs;
- Data Flows;
- SinkClosure / IngressInventory;
- Tool Executions;
- stdout hashes;
- Runtime Facts;
- Review Findings;
- Hypotheses;
- machine assessment;
- `ProposedNonLocus`;
- `LocusAnnotations`;
- falsifier details;
- negative verification internals;
- полный список limitations.

## report.json

Остаётся машинным источником полной информации.

# 15. Machine Assessment

`machineAssessment()` не должен отображаться в основном отчёте после финального verdict.

Особенно запрещена ситуация:

```text
Verdict: EXPLOITABLE
...
Предлагаемая оценка: МОЖНО ОТКЛОНИТЬ ПОСЛЕ ПОДТВЕРЖДЕНИЯ
```

Machine assessment должен отображаться только:

- в `report.audit.md`;
- либо до финального verdict в интерактивном/manual-review workflow.

Если proposal был принят и повлиял на verdict, основной отчёт показывает уже итоговый результат и понятное человеку обоснование.

---

# 16. Источник severity

Не использовать универсальный заголовок:

```text
Исходная оценка (CVE / NVD)
```

если фактический источник неизвестен или другой.

Хранить provenance:

```text
severity_source
score_source
```

Например:

```text
OSV
GHSA
NVD
Scanner input
Ticket
Manual input
```

В отчёте:

```markdown
**Исходная критичность:** MEDIUM, CVSS 5.0  
**Источник:** Scanner input
```

или:

```markdown
**Исходная критичность:** HIGH, CVSS 7.5  
**Источник:** GHSA
```

Если разные источники расходятся, это можно отдельно показать в audit report.

# 17. Предлагаемые изменения модели данных

Рекомендуется постепенно перейти от:

```go
type ContextualRisk struct {
    BaseSeverity
    BaseScore
    ContextualLevel
    ContextualScore
    Priority
    SLA
    Status
    AdjustmentReason
}
```

к модели:

```go
type TriageAssessment struct {
    BaseSeverity       string
    BaseScore          float64
    BasePriority       TriagePriority

    EffectivePriority  TriagePriority
    Disposition        TriageDisposition

    Reason             string
    Preconditions      []TriagePrecondition
    Unknowns           []TriageUnknown

    SeveritySource     string
    ScoreSource        string
}
```

Где:

```go
type TriageDisposition string

const (
    TriageUnchanged    = "UNCHANGED"
    TriageLowered      = "LOWERED"
    TriageDismissed    = "DISMISSED"
    TriageInconclusive = "INCONCLUSIVE"
)
```

Если требуется backward compatibility, старые поля можно оставить в JSON как deprecated.

# 18. Изменения в `internal/risk`

## Обязательные

1. Удалить правило:

```text
EXPLOITABLE + PUBLIC → Contextual CRITICAL / P0
```

как механизм повышения исходной оценки.

2. Ввести clamp:

```text
effective severity cannot exceed base severity
effective priority cannot be more urgent than base priority
```

3. Для `EXPLOITABLE`:

```text
по умолчанию → UNCHANGED
```

4. Снижение разрешать только при подтверждённом mitigating factor.

5. Unknown exposure/auth/deployment не использовать для безопасного снижения.

6. `INCONCLUSIVE` не должен автоматически снижать P0 до P1 или P2.

# 22. Тесты

Добавить регрессионные тесты.

## Triage monotonicity

```text
base MEDIUM/P2 + exploitable/public → <= MEDIUM/P2
base HIGH/P1 + exploitable/public → <= HIGH/P1
base CRITICAL/P0 + mitigations → P1/P2 allowed
base P2 → P0 forbidden
base P1 → P0 forbidden
```

Полезно реализовать property-style test:

```text
effectivePriority must never be more urgent than basePriority
```

## Report contradictions

Тест должен падать, если одновременно присутствуют:

```text
EXPLOITABLE
МОЖНО ОТКЛОНИТЬ
```

или:

```text
NOT_AFFECTED
требуется первоочередное исправление
```

## LLM reporting

При `LLM adapters disabled`:

```text
report.md contains "LLM-анализ ... не выполнялся"
report.md does not claim that LLM semantic analysis was performed
```

## Deployment scenarios

Неподтверждённый Mesh / NetworkPolicy должен отображаться как:

```text
условие возможной переоценки
```

а не:

```text
NO_EXPLOIT_PATH_FOUND / DISMISSED
```
