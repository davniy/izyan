# Task 6 — Проверка структурированного Evidence Contract

**Цель:** установить, позволяют ли структурированные доказательства получать безопасные отрицательные решения от Agent и нужна ли для этого отдельная независимая проверка. **Разработку production Verification Gate пока не начинать.**

## 1. Предпосылки

В offline-replay Task 5 обнаружены два механизма False-Safe: `ERROR` принят за отсутствие пути и `0 results / PARTIAL scope` обобщён до глобальной недостижимости. Ответы агентов почти всегда содержат лишь `category` и `reasoning`, поэтому проверить связь между отрицательным claim, областью и конкретным evidence нельзя.

До использования текущих метрик перепроверить scorer: `19 + 26 < 46` для объединения блокировок невозможно; отличать **попытки** от **уникальных кейсов** (`testify` — три попытки одного кейса).

## 2. Экспериментальные режимы

- **P2:** Qwen 3.6, улучшенный промпт P1 + обязательный структурированный assessment, **без MCP**.
- **T2:** тот же промпт и схема, но с MCP Evidence Tools Izyan. Отличие от P2 — только блок инструментов и их доступность.
- **V-P2 / V-T2:** offline validation **тех же сохранённых** ответов P2/T2. Модель повторно не вызывается.

P1/T1 (Task 5) сохраняются как исторические контрольные результаты; если нужно количественно приписать изменения *только* новому формату промпта, контрольный P1/T1 должен запускаться в сопоставимых условиях, а не сравниваться с несопоставимым runtime.

## 3. Контракт AgentAssessment

Agent возвращает строгий JSON:

- `category` — одна из категорий VEX-Bench, включая `uncertain`;
- `mechanisms[]` — проверенные проявления/пути CVE, с `subject`, `scope` и ограничениями;
- `negative_claims[]` — **атомарные** утверждения с `predicate`, `subject` (module/package/symbol), `scope` (build tags, platform, call context, рассматриваемый механизм), `evidence_refs[]`, `limitations[]`;
- `unresolved[]` — неисследованные альтернативные пути, ошибки и неразрешённые условия;
- `reasoning` — человекочитаемое объяснение, **не доказательство**.

Ссылки: `src:<path>:<line>@<snapshot-hash>` — проверяемая позиция исходника; `ev:<id>` — идентификатор фактического MCP observation. Для P2 доступны только source refs; T2 может использовать оба вида. Слова `COMPLETE`, `safe` и уверенность самой модели **не являются подтверждением полноты**.

## 4. Минимальный независимый валидатор (offline, не production Gate)

Проверяет без LLM:

1. Schema, существование всех `evidence_refs`, соответствие хэшу snapshot.
2. Отсутствие использования `ERROR`, `UNKNOWN`, `PARTIAL` и пустой выдачи как доказательства глобального отсутствия.
3. Соответствие `subject/scope` утверждения и области observation. Проверка только локального scope не доказывает отсутствие других CVE-механизмов.
4. Для предложения safe-вердикта — явный проверяемый falsifier и достаточное покрытие заявленного CVE scope. Если полноту проверить нельзя — **`INSUFFICIENT_EVIDENCE` / abstain**, не safe.

Валидатор **не обязан** доказывать семантическую корректность сложного Go-анализа по строкам файла; неподдержанные доказательства маркируются `UNVERIFIABLE`, а не автоматически принимаются. Итоговый `category` агента и решение валидатора сохраняются отдельно.

## 5. Порядок и оценка

1. **Smoke:** `k8s-44487`, `k8s-3121`, `rancher-47914`, `testify-28948` плюс 3–4 корректных safe-кейса. Проверить парсинг, ref binding и содержательность scope.
2. **Development:** заморозить промпты/схему/валидатор, затем 30 Go-кейсов × 3 повтора для P2/T2. Ровно одинаковый model/runtime/harness/timeout; Docker, GT вне контейнера. Никаких outcome-driven retries.
3. **Offline replay:** те же ответы оценить с валидатором и без него; **не менять ответы агента**.
4. **Holdout:** после заморозки критериев — новые, не использованные при разработке кейсы/проекты. Без holdout — только предварительный результат.

Метрики: `False-Safe`, `Safe Clear Rate`, `EXPLOITABLE recall`, `FAILED`, `abstain`, доля валидных структурированных claims, доля реально проверяемых negative claims, операционная стоимость. Отдельно — **FS blocked / correct safe lost**, по попыткам и уникальным кейсам; сравнение P2↔T2 и исходных ответов↔валидатору.

## 6. Критерии решения

- **Contract неработоспособен:** большая часть negative claims не имеет проверяемой связи со scope/evidence → не строить Gate; пересмотреть формат/подход.
- **Prompt-only достаточен:** P2 снижает FS без неприемлемой потери SCR → предпочесть более простую архитектуру.
- **MCP доказанно полезен:** T2 лучше P2 по заранее заявленным safety/utility метрикам при приемлемой стоимости → оставить только доказавшие пользу инструменты.
- **Валидатор полезен:** независимо блокирует опасные safe-решения с заранее установленным приемлемым снижением SCR на holdout → только тогда планировать production Verification Gate.

**Результат Task 6:** отчёт о проверяемости Evidence Contract и сравнение четырёх проекций (P2, T2, V-P2, V-T2), **не** новая production-архитектура.
