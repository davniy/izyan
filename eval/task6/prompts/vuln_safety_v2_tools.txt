<CLASSIFICATION_CATEGORIES>
The 12 categories are listed below in STRICT LOGICAL PRECEDENCE ORDER. When evaluating, walk through the list from top to bottom and select the FIRST category that applies. Do not skip ahead.

1. "false_positive"
   - The CVE-to-package mapping is wrong (named package is not what the CVE applies to, or the CVE is withdrawn/malformed). Use only with concrete evidence of mismatch.

2. "code_not_present"
   - The vulnerable package/module is absent from the repository: not declared in any manifest, not in any lockfile, no vendored copy.

3. "code_not_reachable"
   - The vulnerable code is present (manifest, lockfile, or vendored copy) in the codebase but is never executed at runtime, e.g., never imported, referenced, or called from first-party source.
   - Only applicable when code IS present AND call-chain/reachability analysis confirms no execution path leads to it.

4. "requires_configuration"
   - Exploitation requires a specific configuration option, feature flag, or setting that is currently disabled by default in this repository.

5. "requires_dependency"
   - Exploitation requires an additional dependency (library, plugin, module) that this repository does not declare.

6. "requires_environment"
   - Exploitation requires a specific runtime environment (OS, architecture, kernel version, hardware feature) that this repository does not establish or rely on.

7. "compiler_protected"
   - Compile-time hardening configured in this repository's build (stack canaries, PIE/ASLR-required builds, sanitizer instrumentation, etc.) prevents the exploit primitive.

8. "runtime_protected"
   - Runtime mechanisms set up by this repository's own code (sandboxing, in-process isolation, seccomp filters) prevent exploitation.

9. "perimeter_protected"
   - Network, authentication, or perimeter controls shipped in this repository (auth middleware, allowlists, network policies in deployment manifests) block the attack surface.

10. "mitigating_control_protected"
    - Other in-repo mitigations not covered by 7-9 (input validation, output encoding, custom guards) reduce risk to negligible.

11. "uncertain"
    - Investigation cannot establish presence, reachability, or mitigation status with the available evidence. Use as a true fallback, not a hedge.

12. "vulnerable"
   - All of:
    - an affected version of the vulnerable package is present,
    - the vulnerable surface is imported and called from first-party (non-test) source,
    - no mitigation from categories 4-10 applies.
</CLASSIFICATION_CATEGORIES>

<DECISION_RULES>
1. A CVE is classified as "vulnerable" if and only if ALL of the following hold:
   - The vulnerable code is PRESENT in the container/codebase.
   - The vulnerable code is USED or CALLED by the application.
   - The vulnerable code is REACHABLE from an attack surface (user input, network input, file processing, IPC, etc.).
   - No effective mitigations or protections are in place.

2. If ANY of the above conditions fails, select the SINGLE most appropriate non-vulnerable category by walking the precedence list from top (1) to bottom (11) and choosing the first matching category. For example:
   - If the vulnerable code is not present → "code_not_present" (do NOT also consider "code_not_reachable" or environment factors).
   - If the code is present but unreachable → "code_not_reachable" (do NOT fall through to "requires_environment").
   - If a required dependency is missing → "requires_dependency".
   - If the vulnerable code is prevented by a default or clearly setted configuration" → "requires_configuration".

3. Use "uncertain" only when the investigation genuinely lacks the evidence needed to reach any conclusion.
</DECISION_RULES>

</EXAMPLE>

<SAFETY_RULES>
1. Separate local observations from your final conclusion. "no matches",
   "not imported", "fix found", "default=false", or "OK/COMPLETE" from one
   query does not prove that the CVE is not exploitable.
2. Check alternative manifestations of the defect. Advisory packages,
   fix diffs and affected symbols may not exhaust runtime manifestations.
   Check relevant versions, transitive implementations, generated runtime
   code and dependency-internal calls.
3. A negative conclusion requires a countercheck. Before a safe answer,
   state the necessary exploitation condition, scope, alternatives checked,
   supporting facts and remaining limitations. If a material alternative
   remains unchecked, choose "uncertain".
4. Do not turn failures into absence. A tool error, timeout, PARTIAL result,
   failed build, missing toolchain or unverified deployment fact leaves the
   relevant condition open.
5. Exploitability is not one reachability fact. Absence of a direct
   first-party import does not exclude a transitive path; a single
   reachability observation is not a global exploitability conclusion.
6. Return the single structured benchmark JSON with its official category
   and concrete reasoning, including scope and limitations. Do not invent
   evidence IDs. "uncertain" is an abstention, not a safe conclusion.
</SAFETY_RULES>

  "reasoning": "<evidence-based explanation>",
  "assessment": {

        "subject": "<affected module, package or symbol this manifestation covers>",
        "scope": "<build tags, platform, call context and mechanism boundary you actually verified>",
        "limitations": ["<what this manifestation check could not cover>"]
      }

    "negative_claims": [
      {
        "predicate": "<one atomic negative assertion: e.g. absent / unreachable / fixed-version>",
        "subject": "<module, package or symbol the claim is about>",
        "scope": "<the scope the claim is restricted to: build tags, platform, call context, considered mechanism>",
        "evidence_refs": ["<evidence reference supporting THIS claim>"],
        "limitations": ["<what this claim does not establish>"]
      }
    ],
    "unresolved": ["<unexplored alternative path, tool error or unresolved condition>"],
    "reasoning": "<human-readable explanation of the assessment - not proof>"
  }
}

Rules:
- "category" and "reasoning" at top level stay EXACTLY as specified in
  <OUTPUT_FORMAT>: official category name, evidence-grounded reasoning.
- Split claims into atomic predicates: one negative assertion per entry,
  each with its own subject, scope and evidence. Never bundle a global
  conclusion into a single vague claim.
- evidence_refs bind each claim to checkable evidence, in exactly these
  forms:
    "file:<path>[:<line>[-<line>]]"    - a location you verified in this
        tree. After "file:" write ONLY the path and optional line(s) -
        no package names, versions or commentary. INVALID:
        "file:go.sum:github.com/x v1 entries" (free text after the
        path). VALID: "file:go.sum:12" or "file:go.sum".
    "src:<path>#L<line>@<snapshot-hash>" - a tool-reported source position;
        append the snapshot hash printed by get_product_snapshot
    "sha256:<64 lowercase hex>"        - a payload digest emitted by a tool
    "ev:OBS-NNNN"                      - an observation id emitted by a tool
    "url:https://..."                  - a public advisory or fix document
  Cite only refs that exist. "src:", "sha256:" and "ev:" refs resolve to
  recorded tool output - if no evidence tools are connected, use "file:"
  and "url:" refs. Never invent observation ids, hashes or paths.
- For a safe category (any of the first ten in the precedence list),
  include at least one negative_claim with non-empty evidence_refs that
  states WHY the CVE cannot manifest - the falsifier you checked. A safe
  verdict resting on no checkable negative claim is not a verified answer.
- Record every unexplored alternative path, failed or partial check in
  "unresolved". A safe category with a non-empty "unresolved" list is a
  defect - choose "uncertain" instead.
- "assessment.reasoning" is context for a human reviewer, not proof: the
  words COMPLETE or "safe" and your own confidence are not evidence of
  coverage.
- Do NOT include task ids, snapshot hashes (except inside evidence_refs),
  model or tool versions, token counts or timings inside "assessment" -
  those are recorded by the harness.
- If you genuinely cannot reach a conclusion, keep "category": "uncertain"
  and explain the open conditions in "unresolved". Do not emit a safe
  category as a hedge.
- Reminder: emit exactly ONE JSON object as your whole response - no
  markdown table, no headings, no prose outside the object.
</STRUCTURED_ASSESSMENT>

An MCP tool server named "izyan" is connected to this session. It exposes

Every tool call returns an Observation object:

Binding interpretation rules:
- tool_status "OK" with an EMPTY result is NOT a safety finding.
    completeness="COMPLETE" means "absent inside the closed scope named in

    completeness="PARTIAL"  means "not found in the checked part only";
    completeness="UNKNOWN"  means coverage could not be characterized.
- tool_status "ERROR" means the check failed (no coverage claim);
  "UNSUPPORTED" means the capability is not available in this session.
- Never treat a PARTIAL/UNKNOWN negative, or an absent tool result, as
  evidence that a code path is safe or unreachable.
- scope_details is authoritative: it lists the build context, packages,
  skipped packages and limits that bounded the check. Product-scope
  results say nothing about dependency-internal, dynamically dispatched
  or other-build-configuration behavior unless the scope says so.
- When you cite tool output in
  assessment.negative_claims[].evidence_refs, use the Observation
  "evidence_refs" entries verbatim (they resolve to the recorded tool
  artifact).
